# 满族音乐 · 桌面封装交付前技术审查

> 审查范围：`/Applications/满族音乐.app`（包内 4147 行 `mountainriverechoes.py` + `manchu.html/js/css`）、安装盘 dmg、`Zeqqqnl/packaging` 构建脚本、曲库维护脚本。全程只读检查，未修改任何代码文件。

## 一、架构评价

**方案成立。** Flask 单进程内嵌 + python-build-standalone 便携运行时 + bash 启动器，规避了 PyInstaller 对 `musicdl`/`yt-dlp` 动态导入的打包地狱，对课程作业是合理取舍。三处真正的工程亮点：

1. **单实例锁闭环**（`Contents/MacOS/launcher`）：`mkdir server.lock` 原子竞争得锁 → 写入 `$$` → `exec python3 launcher.py` 顶替本 shell，**PID 不变**，故锁内 PID 恒等于服务进程 PID，`kill -0` 可精确判活，持锁者死则 `rm` 重抢。实测锁内 pid=69728 与 lsof 监听 8767 的进程完全一致。
2. **字节码外移保护签名**：`PYTHONDONTWRITEBYTECODE=1` + `PYTHONPYCACHEPREFIX` 指向数据目录。ad-hoc 签名的 bundle 内多出任何文件都会破封印、被 Gatekeeper 判为"已损坏"。实测包内 `.pyc` 0 个、`__pycache__` 0 个——最易踩的坑已解决。
3. **数据与代码分离**：`MRE_DATA_DIR`（`mountainriverechoes.py:35`）重定向可写数据，`seed_topic()` 按字节比对播种曲库；端口优先 8767（避开山河回响 8766），被占则 `pick_port()` 退回 port 0 并写 `server.port`；就绪判定用 `/api/topics` 是否含 `t03` 且 `--noproxy '*'` 绕代理；shell 与 `already_running()` 双层检查防双击竞态。

**风险点**：仍用 Werkzeug 开发服务器（`app.run(threaded=True)`，server.log 有官方 WARNING），无线程/连接上限，`/api/preview` 每次拖动都占一条上游连接；另有遗留 dev 进程（pid 61957）仍跑源树旧版（4010 行，无 resolve/probe），若它先占 8767，.app 会退到随机端口，与文档写死的 8767 对不上——交付前应先清掉。

## 二、发现的问题（按严重程度）

**致命**

1. **包内代码从未回写源树**。包内 `mountainriverechoes.py` 4147 行/224605 B（10-15 18:46），源树 `Zeqqqnl/webui/` 同名为 4010 行/218320 B（10-11），且源树中 `api/resolve`、`api/probe/start` 出现 **0 次**——新加的四个接口只存在于 /Applications 的包里。
2. **构建脚本漏掉前端资源**。`Zeqqqnl/packaging/build_app.sh` 只 copy 主程序、`templates/`、`musicdl/`、曲库 JSON，**没有 `static/`**；且源树 `webui/` 下本不存在 `static/`，`templates/` 里只有 `mountainriverechoes.html` 而无 `manchu.html`。manchu 三件套是 10-15 手工塞进 .app 的，按脚本重建得到的是山河回响通用页。
3. **曲库三处不一致**：源树 180479 B（83 首）/ 包内与数据目录 197831 B（96 首）。变动报告的 96 首只对得上包内那一份。

**一般**

4. `/api/resolve` 第 2110 行 `float(data.get('dur') or 0)` 无 try 兜底，实测 POST `{"dur":"abc"}` 直接 500，前端只收到 audio error。
5. `/api/resolve` 每次 `new_session()`，而 `search_sessions` 上限仅 16。`_song_session_sid()` 的注释自己写明"每次新建会把正在播放的会话挤掉（止播/404）"，此处违反了自己定的约定：逐首换源十几次就挤掉主会话与常驻索引会话，之后 `/api/preview` 只能靠 `_library_song_lookup()` 兜底，而兜底拿不到 `mc.default_download_headers`，防盗链缺失又触发一轮重搜。
6. `/api/resolve` 串行遍历 5 个源且无超时，项目里已有 `_search_with_timeout()`（1703 行）却未复用，单源卡住即整条挂起。
7. `/api/probe/start`（2208-2216 行）的 `outdir` 完全未校验，`os.makedirs` + 写 `%02d.json`，等于给任何能访问 127.0.0.1:8767 的本地进程一个"任意目录写文件"原语（服务无鉴权、无 CSRF）。建议限定白名单前缀。（`/api/preview` 不接路径，实测 `sid=../../etc/passwd` 仅 404，无穿越问题。）
8. `_probe_worker` 无顶层 try/except，除 `get_client`、`json.dump` 外任何异常都让线程静默退出，job 永远停在 `running`，`probe.py` 白等 180 秒。建议补 `finally: job['state']='done'`。
9. 前端 `heal()`（manchu.js:255）按 `state.view[state.idx]` 定位，自愈异步期间改搜索/排序会让下标指向别的曲目，换到的新源播错歌；成功后 `t.src` 未更新为 `d.source`，"八旗"色点仍显示旧音源。
10. 歌词三位毫秒错位：`parseLyric` 的 `+m[3]/100` 把 `[00:12.345]` 算成 15.45 秒，应按 `10 ** m[3].length` 归一。网易云两位格式不受影响，酷狗/酷我三位格式整体偏移。
11. `loadFav()`（manchu.js:123）"远端非空即覆盖本地"，未做时间戳合并；后端 `/api/ui/state` 已有 `_sane_ui_ts` 新者胜机制，前端却没读 `t` 字段，清缓存后本地收藏会被静默丢弃。

**建议**：Werkzeug 换 waitress；体积 161 MB 中 runtime 占 156 MB（96.9%），`Crypto` 与 `Cryptodome`（同一库两个发行名，各 7.7 MB）重复，`pip` 6.3 MB、`pygments` 5.0 MB 与运行无关，可再省约 20 MB；交付前把包内 4147 行版 + `static/` + `manchu.html` + 197831 B 曲库回写 `Zeqqqnl/`，并在 build_app.sh 补一行 `rsync -a "$ROOT/webui/static/"`。

## 三、封装与签名结论

`codesign --verify --deep --strict` 退出码 0，包体自洽：`Signature=adhoc`、`TeamIdentifier=not set`、`Sealed Resources…files=5730`。但 `spctl --assess` 返回 **rejected**——ad-hoc 无开发者证书、未公证：本机可跑，换机器双击会被 Gatekeeper 拦，需右键→打开或 `xattr -dr com.apple.quarantine`。报告里应如实写"未公证，需手动授权"，不能写成"已签名可分发"。

安装盘 56.9 MB（UDZO/zlib，压缩率 0.329），含 Applications 快捷方式与 dmgbuild 特征文件（`.background.tiff`、`.DS_Store`），内容与 /Applications 下的 app 一致。**可复现性不足**：真实脚本在 `Zeqqqnl/packaging/`，而非 `民族音乐/packaging/`（后者只有 `dmg_settings.py`，且其 `files` 依赖先装好的 app）；`build_app.sh` 的 `ROOT` 写死绝对路径；`dmgbuild` 当前未安装，最终盘的构建环境已不可复现；`build_dmg.sh` 是另一条 hdiutil 路径，两者并存易混淆。

## 四、总体结论

**满族音乐独立应用采用 Flask 单进程内嵌 + python-build-standalone 便携运行时 + ad-hoc 签名的封装方案，以 mkdir 原子锁实现单实例、以字节码外移保护签名封印，包体自洽校验通过、96 首曲库可正常起播；主要遗留问题是新增接口与前端资源未回写源树导致构建脚本无法从零复现，以及 ad-hoc 签名未公证需在目标机器手动授权。**
